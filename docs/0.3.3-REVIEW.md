# Cardtunes 0.3.3 Review and Acceptance

Review date: 2026-09-06. Scope: saved playlists, games, larger libraries,
incremental rescans/battery display, and ordered Spotify imports, starting at
`3f40503`. The release branch is `feature/spotify-folder-playlists`.

The requested `/review` included a primary source review and an independent
same-host Codex review. It was not a cross-model review. Follow-up passes checked
the fixes and API/client contracts. Original Cardtunes code is MIT licensed;
dependencies retain their existing notices. Music and credentials are excluded.

## Findings Fixed

- Playlist JSON now has pre-parse depth bounds. Legacy JSON also has a node
  budget, preventing small, shallow files from allocating thousands of nodes.
- Imported repeated songs retain their entry identity through playback,
  next/previous, shuffle startup, edits, and saved-position restoration.
  Removing the playing occurrence stops it even when the same song remains.
- Uploading a missing song refreshes the active playlist without clearing its
  queue, history, or existing shuffle permutation.
- ID3 inspection stops after 64 frames. Huge chains of tiny metadata frames
  cannot monopolize one incremental scan step; audio offsets remain correct.
- Library, playlist, and queue responses are paginated at eight entries.
  Browser and CLI queue readers aggregate pages, including older unpaged APIs.
- Response-array ownership and allocation checks prevent unattached cJSON
  leaks; failed serialization returns HTTP 503 instead of a successful `{}`.
- Playlist resolution uses one sequential index reader and compact lookup
  keys. Hash matches are always checked against the complete path.
- The audio worker reserves 24 KB, following measured use of about 18 KB.
  `audio_stack_free` and `heap_largest_block` expose ongoing diagnostics.

## Reboot Investigation

A captured panic during simultaneous rescanning and an allowed 64-track library
request showed mDNS receive allocation failure, followed by ESP-IDF logging and
`lock_init_generic` aborting when it could not allocate its lazy UART lock.
This is a confirmed reproduced failure path, not proof of every historical reset.

Besides bounded response memory and smaller working allocations, the UART logger
is initialized before Wi-Fi. Reporting a low-memory network event must not itself
try to initialize the logging mutex. Temporary panic-capture code is not part
of the release build.

## Verification

- Native ASan/UBSan: MP3 decoding/seeking, malformed metadata, 100,000-frame
  tag chains, playlist validation/recovery, JSON guards, repeated positions,
  shuffle cycles, upload refresh, and 10,000-track scan fixtures.
- Games: real engine tests, 60,000 fuzz steps, save/recovery and render bounds.
  Actual-device checks cover all three games, input/pause/exit, SD saves,
  and restoring the same music selection and queue.
- Go race tests and vet; Playwright browser tests cover playlist and queue
  pagination, duplicate selection, failed/stale requests, and responsive layouts.
- Actual-device scan cancellation retains the complete previous index. An
  803-track full scan with repeated large-page requests completed in 153,307 ms
  without a reset; maximum observed status response was 1,840 ms.
- Hardware checks passed a 64-entry queue, malformed import rejection,
  repeated-entry edits, 1,000-entry import/selection, and missing-song uploads.
- All paths and positions in four imported definitions are compared against
  their source exports. Repeated-occurrence playback is checked, not just JSON.
- Real screenshots verify the battery outline/terminal and nonblank game views.
- Git history, tracked/new source, and GitHub discussion metadata were scanned
  for credentials before public publication. Private build artifacts stay ignored.

## Limits

Transient heap minima can still become very low during Wi-Fi/storage stress;
this board has no PSRAM. These tests are not an indefinite reliability soak.
API allocation failures are reviewed structurally, not injected into the live
device. Legacy version-1 files still use the original whole-file parser; its
maximum valid long-path RAM footprint has not been verified on hardware.
Version-2/3 playlist storage uses bounded streaming reads/writes.
Sudden power loss and FAT faults are simulated in native tests, not
deliberately induced on the owner's card. Physical keyboard feel remains a
human acceptance check.

Folder names and filenames do not contain Spotify's playlist order. The import
tool requires an existing export with `list_position`; unavailable songs remain
visible as missing entries until their files are copied and indexed.

The battery percentage is estimated. Cardputer-Adv hardware does not expose
charging status/current, so no misleading charging indicator is displayed.
See [M5Stack's battery documentation](https://docs.m5stack.com/en/arduino/m5cardputer/battery).
